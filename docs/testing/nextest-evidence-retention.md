# Retaining core Nextest telemetry

Issue [#110](https://github.com/OpenCoven/coven-threads/issues/110) owns this additive core CI evidence profile. It is separate from [native daemon retention](daemon-evidence-retention.md) and the declared #111 window. A Nextest pass cannot qualify a daemon journey. These commands only consume existing completed GitHub Actions evidence; they never dispatch, retry, change a workflow or modify a runtime audit store.

Use Node 24.22.0, Python 3.11+ and an existing authenticated GitHub CLI. Supply an explicit run and attempt and a new dedicated core archive outside tracked source:

```bash
node scripts/retain-nextest-evidence.mjs RUN_ID ATTEMPT DEDICATED_CORE_ARCHIVE
node scripts/retain-nextest-evidence.mjs --summary DEDICATED_CORE_ARCHIVE
```

The archive has a core-only profile marker and refuses an unmarked nonempty directory, including a native archive. Its immutable identity is run/attempt. It retains complete paginated before/after REST snapshots, original available ZIP/log bytes, source commit/tree/configuration responses, extracted JUnit, derived record/packet and a SHA-256 index. Conflicting bytes never replace the original identity. Identical re-ingestion is idempotent. Metadata/transport failures preserve indexed staging snapshots; unavailable optional artifact evidence remains a canonical negative observation with a replayable transport-failure receipt.

Collection accepts only completed `.github/workflows/ci.yml` attempts in OpenCoven/coven-threads and the uniquely named Nextest job. The existing producer's generic `nextest-junit` artifact name does not identify an attempt. The consumer binds a unique artifact to its run/source and the actual upload step's timestamp interval. Duplicate jobs/artifacts, foreign source, incomplete pagination and metadata changes refuse collection. Missing, expired, cancelled, skipped, failed or unbound evidence never supplies a first-attempt pass.

Original ZIPs must match GitHub's digest and size, pass the existing bounded CRC/path/regular-file checks, and contain exactly `junit.xml`. The bounded Python parser rejects XML declarations with entities/DTDs, unsupported structure, duplicate testcase identities, zero tests, invalid timestamps and contradictory root/suite counts. It derives counters from unique cases while preserving terminal failure/error/skipped outcomes and each flaky/rerun marker. Original XML retains messages, outputs and timestamps. [Nextest's JUnit contract](https://nexte.st/docs/machine-readable/junit/) distinguishes flaky recovery from unsuccessful reruns; a flaky-fail case may have both a terminal failure and flaky markers and still represents one test.

Positive core execution requires a clean, nonzero report with every test passing on its first execution, successful job/test-step metadata, the actual command/profile, matching report UUID in the hosted invocation, report time inside that execution step and a matching hosted summary denominator. Actual checkout SHA comes from the checkout action's log and binds GitHub commit/tree metadata; a PR test merge must name the run head as a parent. Tracked Rust blob identities and configuration/lock bytes are retained from that exact tree, with configuration Git blob and SHA-256 checks. Hosted Rust/Nextest versions, host and image identify comparison scope. Source paths, configuration hashes and test identity sets also bind the scope; source/tree identities remain explicit per observation.

The legacy producer does not emit actual Cargo version, resolved feature inventory or test executable hashes. These fields remain unknown rather than fabricated. Hosted checkout/tool logs are provenance observations, not proof against a compromised runner or transient source mutation. A valid report with an unproven source binding remains a negative observation: reported counts are retained but cannot qualify execution. Offline hashes detect changed bytes; authenticated collection/live provenance checks remain necessary to establish that API/log responses are genuine.

Summary generation verifies the complete artifact index and deterministically rebuilds every saved record from original snapshot/ZIP/log/configuration bytes, including negatives. Coherently editing a record and its file index cannot manufacture a pass. Summaries keep events and comparison scopes separate, report observed original attempts and missing originals, retain report-level retry counts, and distinguish later workflow recovery. Later success never replaces the original failure and never proves a causal flaky-test diagnosis. Unknown/unbound report scopes and incomplete collection snapshots stay explicit.

The observed-record denominator does not infer missing CI invocations or a schedule. Existing CI JUnit uploads retain for 14 days; this consumer archives downloaded bytes beyond that hosted limit but neither changes the producer retention setting nor installs an automatic collector. Historical expired/missing bytes cannot be reconstructed, collection cadence still needs its own operating decision, and an entire 30-day retained window requires actual evidence. Never count native or synthetic controls toward that window.

Rollback is a reviewed revert of this additive consumer/parser/tests/docs while preserving original archive bytes, failures, metadata and source receipts. Existing native validation, required checks, producer workflow, daemon pin and human gates remain unchanged.
