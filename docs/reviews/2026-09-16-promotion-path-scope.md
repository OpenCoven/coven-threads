# Scope — the `Channel::Deliberate` promotion submission path (`threads-xpo`)

Dated scope for the daemon-side promotion-write path required by
`docs/seam-promotion-write-contract.md`. It is a plan and an evidence record,
not an implementation and not an authorization to build. Every claim below was
verified on 2026-09-16 against `origin/main` of the named repository.

## 1. Why a scope was needed

`threads-xpo` reads as one missing feature: the daemon never constructs
`Channel::Deliberate`. That is true, but it is the smallest part of the gap. The
surrounding machinery — a scratch tier to promote from, a reachable promotion
module, an admission audit event, and a resolvable provenance anchor — is also
absent, and two of those were blocked on decisions rather than effort.

**Status since publication.** The provenance-anchor decision (§3.1) was settled
on 2026-09-16 and `threads-vd8` is closed; it produced a prerequisite larger
than itself, `threads-vdv`. The `Deliberate` coverage decision (§3.2) remains
open as `threads-7gw`. The rest of the scope stands as written.

Scoping first avoids starting at the visible symptom and discovering the real
blockers halfway in.

## 2. What is already done

This is the encouraging half, and it is larger than expected.

**The decision, audit and approval half of the daemon is already
channel-generic, end to end.** The staged pending-proposal envelope carries
`channel` as a required field, and roughly twenty downstream sites pass
`pending.channel` through rather than re-deriving it. The approve/reject
lifecycle never assumes `Mutation`.

`ward_audit` persists the channel as a lowercased string, and the census
classifier in `crates/coven-cli/src/ward_audit_census.rs` already decodes
`"deliberate"`. A `Deliberate` value would round-trip today **with no schema
change and no migration**.

On the Threads side the validator is complete: `Channel::Deliberate` exists,
`required_strand_kinds()` is deliberately empty, `RejectReason::ChannelNotCovered`
already rejects an uncovered channel, and `ApprovalPath::FamiliarCoherence` — the
ceremony §3.1 recommends — exists. All six `RejectReason` and all five
`WindowCloseReason` variants the contract names are real. **The seam needs no new
rejection vocabulary.**

Two corrections to the `threads-xpo` record, which was written 2026-08-09:

- "Every concrete channel the daemon constructs is `Channel::Mutation`" is not
  quite right: `crates/coven-cli/src/store.rs:3444` constructs `Channel::Forced`
  for the WARD-C6 compaction-ledger row.
- "Referenced NOWHERE in the coven daemon" is stale, as §2 of the seam contract
  now records.

Neither correction changes the conclusion: **no production site constructs
`Channel::Deliberate`.**

## 3. The blockers, hardest first

### 3.1 Provenance has no resolvable anchor — decision required

This is the real blocker, and it is not a plumbing problem.

RFC-0001 §5.6 requires `source_attestation` to identify *a prior committed Ward
state or principal-authorized write event*, and requires validation to confirm
that referent **exists in the append-only audit log**. An attestation whose
referent cannot be resolved MUST be rejected. The familiar-contract conformance
corpus carries the worked chain: `ward_updated` → `principal_authorized_write` →
`memory_entry_admitted`.

Against that requirement:

| Event | Generated by the daemon today? |
| --- | --- |
| `ward_updated` | No — no construction site |
| `principal_authorized_write` | No — appears only in an event-tag allowlist and a test |
| `memory_entry_admitted` | No — the constructor's only caller is a Threads unit test |

The daemon calls exactly two audit constructors, `for_apply` and `for_verdict`.
The entire memory-admission family is unimplemented.

Separately, the substrate's attestation type does not have the required shape.
`crates/coven-memory/src/promotion.rs` defines `Attestation { schema,
artifact_sha256 }` — anchored to a redacted artifact **file**. RFC-0001 requires
an anchor into the audit log. These are different things, and no adapter
reconciles them.

`principal_authorized_write` staying unimplemented is not an oversight: the
separate authenticated protected-write authority is deliberately disabled
fail-closed, and OpenCoven/coven#887 closed on that basis. So the only anchor a
promotion could resolve against today is `ward_updated`, which is also never
emitted.

**Decided 2026-09-16 (`threads-vd8`, closed).** Both RFC-0001 referents stay
valid; a promotion admission resolves against **committed Ward state**
(`ward_updated`), while `principal_authorized_write` remains valid but
unreachable while OpenCoven/coven#887 keeps that route disabled fail-closed.
Recorded in §5.1 of the seam contract.

Two consequences followed, and both are larger than the decision itself:

- **`ward_updated` is never emitted either**, so the anchor does not yet exist
  at runtime and every conforming admission would fail closed. Filed as
  `threads-vdv` (P1) and added as a blocker of `threads-xpo`. It is distinct
  from the disabled protected-write authority and must not be used to re-enable
  it.
- **Authorization scope was settled per-admission.** Promotion is a
  self-improvement loop under RFC-0001 §3.4 and unknown origin is treated as
  loop-originated, so every promoted entry carries its own
  `principal_authorization`; a standing, session-wide or batch grant does not
  satisfy §3.4. **Promotion is therefore a review queue, not a background
  process** — which should be weighed before building it.

### 3.2 No thread holds under `Deliberate` — design decision required

`crates/coven-cli/src/threads_gate.rs:57` defines `PROTECTED_CHANNELS` as
`[Forced, Serialization, Mutation]` and uses it in two places: every woven
thread's `holds_under`, and the `AllSurfacesHoldOnChannels` pattern predicate's
required `channels`.

A `Deliberate` request against those threads therefore rejects at
`validate_fail_closed` with `ChannelNotCovered`, before any of the work in §3.3
matters.

The obvious fix — append `Deliberate` to the const — is wrong. `pattern.rs`
states the RFC-0001 §4.1 floor holds under the three channels "where load
arrives without familiar cooperation", and says plainly that **`Deliberate`
coverage is a per-thread choice, not a floor requirement**. Adding it to the
const would raise the structural floor for every protected surface, changing
weave coherence semantics well beyond promotion.

What is needed is per-thread `Deliberate` coverage for promotion-eligible
surfaces, which means separating "channels this thread holds under" from "the
floor the pattern predicate requires". Those are the same value today.

### 3.3 No scratch tier, and the promotion module is unreachable

- The memory store has one tier. `crates/coven-memory/src/db.rs` creates `docs`
  and `meta`; there is no scratch/durable distinction to promote *across*.
- `crates/coven-memory/src/promotion.rs` is a 455-line contract module —
  `PromotionClaim`, a seven-state durable journal, restart reconciliation — whose
  own header says it "deliberately does not expose a write command". It is dead
  code: **`coven-cli` does not depend on `coven-memory`**, so the daemon cannot
  reach it. Nothing in the workspace imports it.
- No promotion surface exists: `MemoryCommand` is `Open | Mobile | Import |
  Restore`, and every memory route is a `GET`.
- The `coven memory promote` milestone (`cmem-1ev`, M2) is recorded in-progress,
  but the working branch its last note describes exists neither in the local
  coven checkout nor on the remote. Treat that work as lost, not resumable.

## 4. Implementation surface, once the decisions land

`threads_gate.rs` is where `Mutation` is nailed down — **five literals and one
const**. Everything downstream already flows a channel.

| Item | Location | Nature |
| --- | --- | --- |
| `PROTECTED_CHANNELS` / weave construction | `threads_gate.rs:57`, used at `:619` and `:645` | §3.2 decision |
| `GateRequest` has no channel field | `threads_gate.rs:299`, literals at `:382`, `:411` | Thread a channel |
| `pending_proposal` | `threads_gate.rs:1334` | Thread a channel |
| `stage_coherence_proposal` lane fray | `threads_gate.rs:1212` | Thread a channel |
| apply-audit persistence | `threads_gate.rs:1064` | Thread a channel |
| New dispatch arm + handler | `api.rs:857` match | New code |
| `memory_entry_admitted` call site | none today | New code |
| CLI verb, if wanted | `main.rs:816` `MemoryCommand` | New code |

Routes must be added to the `api.rs` dispatch behind `normalize_api_route`;
`api_routes.rs:25` explicitly forbids registering them in a helper that skips
the version gate. Transport authority already restricts `/threads/proposals*`
to owner-gated local IPC, and a promotion route should inherit that posture
rather than invent its own.

Already channel-generic, needing no change: `append_apply_audit_records_at`,
`append_proposal_apply_intent`, `append_proposal_refusal_audit`,
`ProposalDecisionAudit`, `ApprovedProposalFinalization`, the whole
approve/reject lifecycle, and `ward_audit` storage plus census decode.

## 5. The one piece that is ready now

`threads-55s` — parameterize `WardAuditRecord::for_memory_entry_admitted` to
accept and record the channel, replacing the hardcoded `channel: None`.

It is low-risk and self-contained: `for_apply` already takes
`channel: Option<Channel>` as precedent, the `channel` column is nullable in
every schema variant, and the `memory_entry_admitted` CHECK constrains only
`detail` — never `channel`. **No migration, no fingerprint change.**

It was blocked on `threads-xpo`, on the reasoning that without a caller able to
supply `Deliberate` the constructor would record `Mutation` forever. That
argument applies to its *end-to-end* acceptance criterion, not to the change
itself, which is a prerequisite for the daemon work rather than a consequence of
it.

**Landed 2026-09-16.** The dependency was removed and the acceptance criterion
split rather than weakened: the constructor half is satisfied here, and the
end-to-end round-trip moved to `threads-xpo`. §5.3 of the seam contract was
updated in the same change so the normative text does not describe a fixed gap
as still open.

## 6. Evidence bar

`docs/testing/e2e-contract.md` defines eight journeys; promotion is not among
them. A promotion path needs a ninth, proving admission, refusal, and the
audit chain through the real daemon boundary with the current Threads checkout
overlaid and proven active.

Per-blocker evidence is the standard already set: a failing black-box case
against pre-fix behavior, the production fix in the canonical owner, a passing
black-box case, a lower-level regression test, a named CI check, and migration
and rollback notes where persistence changes.

A promotion write routed through a veto window also inherits whatever remains
of `threads-980`; §5.2 of the seam contract records that dependency.

## 7. Recommended sequence

1. ~~Land `threads-55s`~~ — done 2026-09-16; no migration, no fingerprint change.
2. ~~Decide provenance anchoring~~ — done 2026-09-16 (`threads-vd8`). It
   produced `threads-vdv`: emit `ward_updated` so the anchor exists.
3. Decide per-thread `Deliberate` coverage versus the structural floor (§3.2).
4. Establish the crate edge or adapter so the daemon can reach promotion (§3.3).
5. Define the scratch tier and the `coven memory promote` surface (M2, `cmem-1ev`).
6. Thread the channel through `threads_gate.rs`; add the route, handler and
   `memory_entry_admitted` emission.
7. Add journey J9 and the red-to-green daemon evidence.

Steps 2 and 3 are decisions, not tasks. Steps 4 and 5 are owned by the coven
monorepo under the Option B ruling that the monorepo crate is the authoritative
substrate; the separate `OpenCoven/coven-memory` repository is a read-only
dashboard and carries spec, plan and beads only.

## 9. What this scope does not do

- It authorizes no implementation. The §3.1 decision was settled separately and
  is recorded in the seam contract, not granted here; the §3.2 decision
  (`threads-7gw`) remains open.
- It closes no bead. `threads-xpo` stays open; the submission path does not exist.
- It changes no normative contract, required pin, or protected path.
- It is not a commitment to build promotion. The §3.1 finding may reasonably
  push the whole feature behind the separate authority work it depends on.
